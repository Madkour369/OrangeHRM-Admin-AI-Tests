OrangeHRM Admin QA Pipeline — Solution Flow

A reusable 5-milestone Spec-Driven Development pipeline (M1–M5), gated G1–G5, that turned .specify/specs/001-admin-ui/spec.md into a governance-compliant Playwright + TypeScript UI suite for OrangeHRM's Admin module. Every artifact named below exists on disk in this repository.

1 · End-to-end pipeline

Milestone N+1 may not begin until milestone N's artifact exists on disk, is non-empty, and passes its Definition of Done (.specify/specs/001-admin-ui/tasks.md). A gate box below is only "open" once that DoD is met.

3 · Feedback loops

What makes this a pipeline rather than a one-way checklist: later milestones correct earlier artifacts, and the correction is recorded at its source, not silently absorbed.

These three loops are recorded, not silent: prd.md §13.1 lists all 7 M2→M1 corrections by requirement and cause; exploration.md's §6 "M5 locator corrections" note and this project's M5 progress log list every M5→M2/M3 correction by cell/finding; healing_process.md's 29 entries each end in a named "Prevention rule," several of which became new fieldFactory.ts or component exports rather than one-off patches.

4 · Framework layering

5 · Reuse for a new module

/new-module <MODULE_CODE> <Module Name> (.claude/commands/new-module.md) runs this whole cycle for a new module, reusing everything built for Admin. It reuses the constitution, plan.md's stack/layers/report schema, and /analyze /coverage /code-review /heal unchanged; it writes only a new spec chapter, src/pages/<module>/, tests/<module>/, and module-suffixed deliverables. A change it finds itself needing below src/pages/ is treated as a framework gap — fixed generically, never patched with a module-specific branch — and its own closing "Reuse report" states new-vs-reused lines and names any such gap explicitly rather than letting it pass silently.

Created new (per new-module.md)

  • prd.md's existing Tier-3 chapter for the module, promoted to Tier 1 in place (full field tables, BR-nn-referencing rules, US-<code>-nn-yy stories with inline Gherkin) — not a new PRD document.
  • .specify/specs/00N-<code>-ui/spec.md (N = next free number), mirroring prd.md's new ids.
  • M2: exploration-<code>.md + evidence-<code>/ — deltas against the existing locator risk register only, not a re-walk from zero.
  • M3: test_design-<code>.csv, same byte-exact header, ids TC_<code>_<sub>_nnn.
  • M4: agent_execution_report-<code>.html — same template, only the injected data object changes.
  • M5: src/pages/<code>/ and tests/<code>/ only, plus healing_process-<code>.md.
  • Any genuinely new oxd primitive → a new, generic class in src/components/ — built once, for every module, never module-specific.

Reused unchanged — DO NOT rewrite

  • /new-module <CODE> <Name> itself — the same command drives every future module's cycle.
  • .specify/memory/constitution.md — same rules, same gates G1–G5.
  • .specify/specs/001-admin-ui/plan.md — same stack, layers, report schema.
  • All 4 pipeline commands: /analyze /coverage /code-review /heal — already module-agnostic.
  • src/components/, src/fixtures/, src/utils/, src/pages/base/ — the framework. A module that seems to need a change here is a framework gap, fixed generically and recorded, never a module-specific branch.
  • deliverables/04-execution/agent_execution_report.html — template plus data object; only the data changes.

This is what CLAUDE.md §4 means by "swapping the module under test must require only a new spec.md + new src/pages/<module>/ + new tests/<module>/" — and it is why 76.4% of this project's own Wave 2 (68 of 89 scheduled cases, as measured when the waves were first sequenced — before 5 cases moved to Wave 1 post-G5) is pure parameter variants against an already-built page object, not new interaction code (test_design_coverage.md, "Execution sequencing" section).
